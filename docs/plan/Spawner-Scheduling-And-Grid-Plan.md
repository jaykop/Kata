# 플레이어 위치 기반 스포너 관리와 타임슬라이싱 계획

작성: 2026-10-06  
갱신: 2026-10-06  
연결 이슈: 미게시. 앞서 조회한 열린 이슈에 직접 대응하는 작업 없음. 기존 스포너 #21의 후속 작업.  
현재 상태 근거: [스포너 사용법](../manual/Spawner.md), 스포너·생성 서브시스템·AI 종료 경로의 관련 소스  
대체 관계: 같은 파일의 위치 배치용 그리드 초안을 이번 목적에 맞춰 개정

## 목적과 현재 상태

목적은 플레이어 위치를 기준으로 주변 스포너의 NPC를 생성하고 멀어진 스포너의 NPC를 제거하면서, 여러 스포너의 위치 계산·생성·제거 비용을 여러 프레임에 분산하는 것이다. 그리드는 주변 스포너를 찾는 공간 인덱스다. NPC를 격자 위치에 배치하는 기능은 이번 범위가 아니다.

사용자가 요청한 것은 구현 계획 정리다. 아래 구성은 코드와 목적에 근거한 권고안이며 아직 구현하거나 사용자 확정 결정으로 간주하지 않는다.

현재 스포너는 단발 생성과 대기 요청 취소를 제공한다. 거리 활성화·디스폰·재진입 정책은 없다. 모든 위치 계산과 요청 제출은 시작 함수에서 처리하고, 캐릭터 로드 완료 콜백은 실제 생성까지 즉시 수행한다. 실제 프레임 비용은 측정하지 않았다.

## 범위

- 포함: 주변 스포너 조회, 거리 활성화 정책, 대기 생성 취소, 스포너가 관리하는 NPC 제거, 위치 계산·생성·제거 타임슬라이싱.
- 제외: NPC 배치 격자·간격 보장, 풀링, 전투 판정, 사망·세이브 상태 보존, 자동 결원 보충, World Partition 자체 구현.
- 모듈: 실행은 KataFramework, 편집 도구는 KataFrameworkEditor. 코어와 위성에 새 관리자를 넣지 않는다.

## 현재 코드 진단

| 코드 | 확인한 구조 | 필요한 변경 |
|---|---|---|
| `AKataCharacterSpawner::SpawnCharacters` | 전체 수량의 후보·NavMesh 재시도·요청 제출을 한 호출에서 처리 | 커서로 위치 준비와 제출을 나눔 |
| `Transforms`, `PlacementFailed`, `PendingRequests` | 전체 수량의 배열·예약 맵을 먼저 생성 | 미처리 수는 카운터로, 처리 중 개체만 저장 |
| `UKataCharacterSpawnSubsystem::HandleAssetsLoaded` | 로드 콜백에서 즉시 실제 생성 | 분산 요청의 로드 완료는 준비 큐로 전환 |
| `GetPendingSpawnCount`, `HandleSpawnCompleted` | 예약 맵 크기로 대기 수와 완료 판단 | 미제출 개체를 포함한 RemainingCount로 완료 판단 |
| `CancelSpawning`, `FinishSpawnBatch` | 대기 핸들만 취소하고 생성 NPC는 유지 | 기존 취소 계약 유지, 디스폰은 별도 명령으로 추가 |
| `SpawnedCharacters` | 이전 배치까지 포함한 약한 NPC 참조 | 거리 관리 대상 세대를 별도로 기록해 제거 범위를 명시 |
| `NavMeshProjection::GetQueryExtent` | 현재 액터 Transform에서 탐색 범위를 계산 | 배치 시작 시 고정한 Transform과 일치시킴 |
| `RequestSpawn` | 매 호출 시 행 복사·로드 목록 수집 | 분산 배치는 시작 시 행을 고정하고 요청 준비량 제한 |
| GameMode·일반 비동기 생성 노드 | 같은 생성 Subsystem을 사용 | 기존 단일 생성 경로는 유지하고 분산 요청을 명시적으로 추가 |
| `AKataAICharacter::EndPlay` | Kata AIController를 UnPossess함 | 디스폰 시 Pawn뿐 아니라 생성한 Controller의 수명도 처리해야 함 |
| `AKataAIController::OnUnPossess` | StateTree를 먼저 중단 | 기존 AI 종료 경로를 사용하고 별도 강제 중단 체계를 중복 구현하지 않음 |

설정 사본의 GC 추적, 배치 ID, 준비 중 재호출 거절, 즉시 실패 콜백과 이벤트 이후 취소 재확인은 보존한다. 컨트롤러가 실제로 남는지는 실행으로 확인해야 하며 소스만으로 누수를 확정하지 않는다.

## 권장 구성과 판단 근거

### 1. UKataSpawnerSubsystem 신규: 월드 관리와 유일한 작업 스케줄러

Tick 가능한 월드 Subsystem으로 둔다. 등록된 스포너의 공간 인덱스, 플레이어 위치 관찰, 활성화 판단, 위치 준비 작업과 디스폰 작업, 공용 프레임 예산을 관리한다. 실제 캐릭터 생성도 아래 생성 Subsystem에 남은 예산 안에서 수행하도록 요청한다.

기존 생성 Subsystem에 공간 관리까지 넣지 않는 이유는 단일 캐릭터 생성 API에 플레이어·거리·스포너 정책을 결합하지 않기 위해서다. 새 관리자는 거리 기능과 타임슬라이싱을 함께 담당하므로 별도의 Grid Subsystem이나 TimeSlicing Subsystem을 추가하지 않는다.

### 2. AKataCharacterSpawner 기존: 개별 배치와 생성 NPC의 관리 주체

설정 사본, 고정한 NPC 행·영역, 배치 ID, 진행 커서, 결과 수량, 거리 관리로 생성한 NPC 세대를 소유한다. 관리자가 지시한 만큼 배치를 진행하거나 자신의 NPC를 제거한다. 액터마다 Tick·거리 타이머를 추가하지 않는다.

거리 상태는 관리자가 결정하며, NPC 참조와 배치 실행 상태는 스포너가 소유한다. 양쪽에 같은 큐나 상태 값을 독립적으로 복제하지 않는다.

### 3. UKataSpawnerComponent_DistanceActivation 신규: 기존 인라인 설정 방식

실제 ActorComponent가 아닌 기존 UKataSpawnerComponent 파생 UObject로 추가한다. SpawnDistance, DespawnDistance와 재활성화 정책을 설정한다. 활성 항목은 하나만 허용한다. 플레이어 조회·거리 검사·큐 처리는 수행하지 않는다.

별도 ActorComponent가 필요 없는 이유는 기능을 기존 전용 스포너에 붙이는 범위이고 이미 인라인 옵션 확장 계약이 있기 때문이다. 일반 Actor에도 이 정책을 부착할 필요가 생길 때 독립 ActorComponent를 검토한다.

타임슬라이싱은 스포너의 실행 방식이므로 기본적으로 관리자가 담당한다. 별도 TimeSlicing 설정 UObject를 필수로 추가하지 않는다. 수동 스포너에는 실행 방식 선택을 제공하고 거리 관리 스포너는 공용 분산 경로를 사용한다.

### 4. UKataCharacterSpawnSubsystem 기존: 비동기 로드와 실제 생성

거리나 플레이어를 알지 않는다. 기존 RequestSpawn은 유지한다. 추가되는 분산 요청은 로드 완료 후 준비 상태로 보관하고, 새 관리자가 호출하는 예산 제한 처리 함수에서 생성한다. 생성 Subsystem에 별도 Tick·자체 프레임 예산을 두지 않아 생성 비용을 두 관리자가 중복 집행하지 않는다.

준비 큐의 공정한 처리와 취소는 요청 그룹 핸들로 구분한다. 스포너 UObject 참조를 기존 생성 Subsystem에 직접 저장하지 않아도 그룹별 순환과 취소가 가능하도록 한다.

| World Partition | 권고 | 로드된 스포너만 등록. 언로드를 넘는 세대·사망 상태 저장은 별도 범위 |

## 그리드 조회 계획

1. BeginPlay에서 거리 관리 스포너를 월드 그리드에 등록하고 EndPlay에서 해제한다. 최초 등록 시 바로 거리 후보 판정을 예약한다.
2. 셀 좌표는 월드 XY 위치를 CellSize로 나눈 뒤 내림하여 구한다. 음수 좌표도 같은 규칙으로 처리한다. 셀에는 약한 스포너 참조와 등록 ID를 저장한다.
3. 비활성 스포너는 원점 셀에 한 번 등록한다. 플레이어 주변 조회 범위는 등록된 최대 SpawnDistance를 포함한다. 거리값이 다른 스포너를 누락하지 않게 한다.
4. 실제 진입은 개별 SpawnDistance의 제곱 거리로 판정한다. 활성·생성 중·제거 중 스포너는 별도 작업 목록에 두고 DespawnDistance 판정을 계속한다. 주변 조회에서 사라졌다고 이탈 판정을 놓치지 않는다.
5. 조회는 일정 간격으로 수행하며 같은 셀 안의 이동도 거리 판정에 반영한다. 셀 변경만을 갱신 조건으로 삼지 않는다. 플레이어 텔레포트 시 새 주변 조회와 이전 활성 목록 이탈 판정을 예약한다.
6. 많은 셀·스포너의 탐색은 커서로 나눠 처리한다. 스캔이 덜 끝난 것을 범위 밖 판정으로 취급하지 않는다. 큐 실행 직전에 최신 플레이어 위치와 등록 ID를 다시 확인한다.
7. 이동 가능한 스포너는 Transform 변경 시 셀 갱신을 알린다. 이를 제공하지 않는 초기 구현이라면 런타임 고정 스포너만 지원한다고 명시한다. 전체 스포너를 매 프레임 다시 인덱싱하지 않는다.

최대 SpawnDistance가 매우 크면 그리드 이점이 작아질 수 있다. 첫 단계는 단일 그리드와 제한된 설정 범위를 사용한다. 다중 크기 그리드는 실제 필요가 확인될 때 추가한다. CellSize는 조회 성능 설정이며 스폰·디스폰 거리와 독립적이다.

## 활성화·디스폰 상태와 수명

| 상태 | 의미 | 전환 |
|---|---|---|
| Inactive | 거리 관리 NPC와 대기 작업이 없음 | 진입 시 생성 예약 |
| Spawning | 배치 준비·로드·생성 진행 중 | 완료 시 Active, 이탈 시 대기 취소 후 Despawning |
| Active | 해당 세대를 관리 중 | 이탈 시 Despawning |
| Despawning | 기존 세대의 NPC 제거 진행 중 | 제거 완료 후 Inactive, 재진입 예약이 있으면 새 배치 시작 |

- Despawning 중 재진입해도 즉시 새 배치를 시작하지 않는다. 기존 세대 정리가 끝난 후 최신 거리 조건으로 다시 시작해 혼합·중복 생성 방지.
- 매 작업에 등록 ID·배치/세대 ID를 확인한다. 취소된 로드·준비 큐는 생성 전에 제거한다. 실제 생성 중 BeginPlay에서 이탈·종료가 발생한 경우, 방금 생성된 NPC의 귀속과 제거를 완료해 미추적 NPC가 남지 않게 한다.
- 디스폰은 CancelSpawning을 먼저 수행한 뒤 해당 거리 관리 세대의 유효 NPC를 순차 제거한다. 기존 CancelSpawning 자체는 NPC를 제거하지 않는다.
- 수동 생성과 거리 관리 생성을 동시에 자동 병합하지 않는다. 거리 관리 모드에서 공개 수동 생성 호출은 거절하는 계약을 권고한다. 외부 시스템의 NPC나 다른 세대는 제거 대상에 포함하지 않는다.
- 실패한 배치·사망한 NPC를 활성 범위 안에서 계속 재생성하지 않는다. 실패·결원 자동 보충은 별도 정책이다.
- Actor.Destroy를 시작한 개체는 제거 처리 완료로 간주하되 엔진의 실제 메모리 회수는 별도다. 풀링과 사망 이벤트를 디스폰으로 대체하지 않는다.
- 스폰한 AIController도 정리 범위에 포함한다. Pawn 종료가 컨트롤러를 UnPossess하므로 참조를 종료 전에 확보하고, 해당 NPC가 생성한 컨트롤러인지 확인해 재사용 중인 외부 Controller를 제거하지 않는다. 기존 AI EndPlay·OnUnPossess 정리 경로를 따른다.
- 거리 관리 스포너 EndPlay는 등록·대기 작업을 해제하고 관리 NPC 정리를 수행한다. 일반 레벨 언로드 때 유지된 월드 관리자가 제거 작업을 넘겨받을 수 있게 한다. 월드 전체 종료는 새 작업이나 결과 이벤트를 예약하지 않는다.
- 거리 관리 모드가 활성화되면 기존 bSpawnOnBeginPlay의 즉시 생성 경로 대신 등록·초기 거리 평가를 사용한다. 관리 옵션이 없는 기존 스포너는 현재 동작을 유지한다.

## 타임슬라이싱과 실행 계약

### 1단계의 호환성 경계

1단계는 배치 고정 정보·진행 커서·결과 집계를 분리한다. 아직 관리자를 추가하지 않고 분리한 작업을 같은 호출에서 끝까지 실행한다. 기존의 전체 후보 사전 확인과 설정 오류 시 제출 전 거절을 유지하므로 후보 위치 배열은 남긴다. 전체 수량만큼 예약 핸들 맵을 만드는 대신 제출 직전에 개체 하나를 등록하고, 전체 미완료 수는 RemainingCount로 관리한다.

NPC 행은 배치 시작 시 고정한다. 기존 Blueprint 보정 훅의 시그니처를 유지하고 C++ 구현은 스포너의 GetSpawnBatchContext를 통해 고정한 영역 기준을 조회한다. 2단계에서 공용 예산과 분산 경로를 연결하며 위치 배열 제거·수락 후 개별 실패 계약을 적용한다. 이번 단계 자체를 성능 개선 측정 결과로 보지 않는다. 결정 이유와 실제 반영 내용은 [배치 실행 분리 기록](../devlog/2026-10-06-Spawner-Batch-Execution.md)에 둔다.

### 2단계 이후의 분산 경로

월드 관리자 한 곳에서 공용 프레임 시간 예산과 작업 종류별 최대 처리 수를 관리한다. 거리 조회, 배치 준비, 위치 선택·보정·재시도, 로드 요청 제출, 준비 완료 생성, 디스폰에 모두 작업량 제한을 둔다. 실제 에셋 로드 자체의 엔진 비용과 GC 시간은 이 예산의 제어 대상이 아니다.

활성 스포너는 순환 처리하고 작업 종류별 처리 기회를 보장한다. 제거 작업이 생성에 계속 밀리거나 하나의 대량 배치가 다른 스포너를 막지 않게 한다. 로드 중+준비 완료 요청을 합한 상한으로 앞서가는 제출을 막는다. 취소된 큐 항목을 버리는 비용도 예산에 포함한다.

시작 시 고정하는 값은 ID, NPC 행, 활성 설정 사본, 수량, 스포너·영역 Transform이다. NavMesh 투영도 이 고정 Context를 사용한다. 커서는 개체 인덱스·재시도·현재 보정 옵션 위치를 보존한다. 설정 UObject 안에는 실행 상태를 저장하지 않는다.

RemainingCount는 아직 성공·실패로 끝나지 않은 모든 개체를 포함한다. 결과 카운터를 먼저 갱신한 뒤 이벤트를 호출하고, 현재 배치 ID와 상태를 다시 확인한다. 개체 결과와 전체 완료를 중복 통지하지 않는다. 취소된 개체는 기존처럼 성공·실패에 포함하지 않는다.

분산 모드의 SpawnCharacters=true는 요청 수락을 의미한다. 시작 시 확인할 수 있는 설정 오류는 false, 수락 후 발견한 위치 실패는 개별 실패로 통지한다. 기존 사전 위치 계산 경로와 차이를 manual에 명시한다.

캐릭터 하나의 Deferred Spawn·행 적용·FinishSpawning·BeginPlay는 한 작업으로 처리한다. 옵션·Blueprint 훅·Destroy도 실행 중간에 강제로 끊지 않는다. 시간 제한은 작업 사이에서 적용하는 부드러운 상한이다. 실제 기본 시간·개수·조회 주기는 사용자 프로파일로 정하고 근거 없는 성능 수치를 확정하지 않는다.

행 사본·설정 참조는 GC 추적 경로에 보관한다. 준비 완료 요청은 실제 소비·취소까지 로드 핸들을 유지한다. 월드 관리자의 스포너·NPC 목록은 약한 참조로 관리한다.

## 작업 순서와 완료 조건

| ID | 우선순위 | 작업 | 선행 조건 | 완료 조건 |
|---|---|---|---|---|
| S1 | 높음 | 배치 실행 상태와 고정 Context 분리 | 실행 계약 선택 | 기존 이벤트·취소 계약 유지, 미제출 수 집계 |
| S2 | 높음 | 신규 관리자와 기존 생성 서비스 연결 | S1 | 수동 분산 배치를 위치 준비부터 실제 생성까지 공용 예산으로 처리 |
| S3 | 높음 | 세대별 NPC 제거와 Controller 수명 처리 | S1 | 취소·부분 생성·재진입에도 미추적 NPC와 중복 세대가 없음 |
| S4 | 높음 | 거리 설정·그리드 등록·활성화 상태 연결 | S2, S3 및 재진입·디스폰 정책 결정 | 진입 생성, 이탈 취소·제거, 경계 왕복 억제 |
| S5 | 보통 | 미리보기·debug·문서 반영 | S4 | 현재 사용 계약과 제한을 설정 화면·manual에서 설명 |

먼저 타임슬라이싱과 디스폰을 각각 완성한 뒤 그리드 활성화를 연결한다. 그리드부터 붙여 동시에 대량 생성·제거를 유발하는 순서를 피한다.

## 영향과 제한

디스폰은 기존 생성 API에 없던 새 수명 동작이다. 전투·사망·세이브 정책과 결합하기 전에 범위를 확정해야 한다. #41의 캐릭터 제거·풀링과 연관되지만 이 계획으로 사망 시스템을 구현하지 않는다.

World Partition #39와 충돌하지 않게 로드된 스포너의 등록 수명을 따른다. 언로드 후 재로드가 새로운 세대가 되는 초기 정책은 영구 상태 보존을 제공하지 않는다.

수동 단일 생성 API는 기존대로 사용할 수 있으며 그 즉시 생성 비용까지 이번 공용 스포너 예산으로 보장하지 않는다. 기존 스포너를 관리 모드로 전환할 때 BeginPlay와 외부 Blueprint의 수동 호출을 정리해야 한다.

## 사용자 확인 항목

구현 완료 조건과 실제 실행 확인은 구분한다. 이번 계획 작성에서는 빌드·테스트·프로파일·별도 검사를 실행하지 않았다. 구현 후 사용자 확인 대상은 다음과 같다.

- 같은 셀 내 이동·경계 왕복·음수 좌표·텔레포트·다층 지형에서 거리 판정.
- 로드 중 이탈, 준비 완료 중 취소, 생성 BeginPlay 안에서 스포너 제거, 디스폰 도중 재진입.
- 여러 스포너의 공용 예산, 이미 로드된 NPC의 대량 생성과 대량 제거.
- AI StateTree 중단과 Pawn·Controller 잔존 여부, 스포너 언로드·월드 종료.
- 기존 수동 스포너·PC 생성·일반 비동기 생성 노드의 동작.
