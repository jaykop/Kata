# 진행도·퀘스트 시스템 사전 검토

작성: 2026-10-11  
갱신: 2026-10-11  
유형: 진단(착수 전 검토)  
대상: 진행도·퀘스트 시스템(미착수)  
기준: `a98780a` 시점의 Kata 문서·소스 대조. 관련 미커밋 변경 없음

## 배경과 결론

진행도와 퀘스트 시스템은 [액션 게임 기반 시스템 로드맵](https://github.com/jaykop/Kata/issues/24)과
[계획](../plan/Action-Game-Systems-Plan.md)의 범위 밖이며 관련 이슈도 없다. 나중에 착수할 때 다시 조사하지 않도록
쓸 만한 구조 후보, 피할 설계, Kata 제약과 착수 시 정할 질문을 미리 정리한다.

결론은 지금 착수하지 않는 것이다. 퀘스트 상태는 세이브에 기대는데 Kata에는 세이브 계층이 없고, 아이템 목표와 보상은
[아이템과 인벤토리](https://github.com/jaykop/Kata/issues/42)가 먼저 있어야 한다. 착수할 때 이 문서의 질문을 출발점으로
plan을 작성한다. 아래 구조는 모두 제안이며 사용자가 확정한 결정이 아니다.

## 변경 또는 진단 내용

### 채택 후보 구조

| 항목 | 구조 후보 | Kata와의 관계·권고 |
|---|---|---|
| 레코드와 계층 | 정적 데이터 에셋에 고유 ID를 가진 항목 트리(퀘스트 묶음 → 퀘스트 → 단계 → 목표)를 둔다. 런타임은 ID로 항목을 찾고 상위·하위를 따라간다 | 식별자를 GUID로 할지 [행 ID 참조](2026-10-04-Data-Collection-Row-Id.md)로 할지 정해야 한다 |
| 설정과 상태 분리 | 에셋은 설정만 가진다. 항목별 상태(Inactive·Active·Success·Failed)는 Subsystem의 맵에 두고, 세이브에는 이 상태만 기록한다 | "에셋 설정과 실행 상태 분리" 원칙과 같은 방향이다 |
| 태그가 붙은 관계 | 항목 사이의 링크에 용도 태그(선행 조건, 성공 시에만 인정 등)를 붙여 관계를 데이터로 적는다 | 태그 루트를 정하면 [게임플레이 태그 루트 목록](../manual/Gameplay-Tags.md)에 추가한다 |
| 단계 진행 규칙 | 퀘스트 활성화 시 첫 단계, 단계 활성화 시 첫 목표를 켠다. 하위 목표가 모두 성공하면 상위를 성공시킨다. 단계를 하나만 활성으로 둘지는 설정으로 둔다 | 자동 진행 규칙과 설정의 단위는 plan에서 정한다 |
| 목표 감시자 | 목표 에셋에 인스턴스드 감시자(Observer) 템플릿을 둔다. 목표가 활성화되면 복제해 실행 인스턴스를 만들고, 완료·취소·종료 시 이벤트 구독을 해제한다 | 실행 태스크의 자원·구독 정리 원칙과 맞는다. 처치 목표는 [사망 흐름](2026-10-11-Character-Death.md), 아이템 목표는 #42에 의존한다 |
| 월드 플래그 | GameplayTag별 정수 카운터(`FGameplayTagCountContainer`)와 값 변경 델리게이트로 "이 사건을 봤는지" 같은 플래그를 기록한다 | 규모가 작고 범용적이어서 퀘스트보다 먼저 도입할 수 있다. 조건은 KataConditions 파생으로 읽는다 |

### 피할 설계

| 항목 | 피할 방식 | 대안 |
|---|---|---|
| 에셋 로드 | Subsystem 초기화 때 Asset Registry 완료를 기다린 뒤 모든 진행도 에셋을 동기로 일괄 로드 | Primary Asset 등록 후 필요한 범위만 비동기 로드. Kata의 비동기 생성 방향과 맞춘다 |
| 상태 의미 중첩 | "맵에 기록이 없으면 미열람"처럼 열람 여부와 진행 상태를 한 맵에 겹쳐 쓰기 | 열람 여부는 별도 집합이나 필드로 둔다 |
| 선행 조건 재귀 | 링크를 따라 재귀 판정하면서 방문 기록을 두지 않기. 순환 링크에서 무한 재귀가 된다 | 방문 집합으로 순환을 끊고, 에디터 데이터 검증에서 순환을 경고한다 |
| 전용 조건 계층 | 진행도 전용 조건 클래스 계층을 따로 만들기 | [KataConditions](../manual/Conditions.md)의 `UKataCondition` 파생으로 진행도 상태 조건을 추가한다 |
| 카탈로그 겸용 | 캐릭터·장비·스킬 같은 기획 데이터를 진행도 레코드에 함께 담기 | 기획 데이터는 데이터 컬렉션과 행 에셋이 맡고, 진행도는 행 ID로 참조만 한다 |
| 전역 접근 | 정적 싱글턴 포인터로 Subsystem에 접근하기. 종료 시 비우지 않으면 PIE 재시작 때 댕글링 포인터가 된다 | 엔진 Subsystem getter를 쓴다 |
| 범위 확장 | 맵 핀·가이드 액터·보상 UI·복제를 진행도 Subsystem에 함께 넣기 | 싱글플레이 전용이므로 복제는 넣지 않는다. 표시·보상은 진행도 상태를 구독하는 별도 계층으로 둔다 |

## 주요 결정과 이유

- **지금 착수하지 않는다.** 세이브 계층과 #42가 없으면 상태 보존·아이템 목표·보상을 가정으로만 설계하게 된다.
- **plan 대신 devlog로 남긴다.** plan은 이슈에 연결된 Large 작업의 설계 문서다. 선행 기반 없이 지금 쓰면 해당 기능이 생길 때 다시 써야 한다.
- **배치 위치는 미정이다.** 코어는 엔진과 GAS에만 의존하고 확장 지점만 제공하므로 퀘스트 계층은 코어 범위가 아니다.
  새 위성 플러그인과 `KataFramework` 중 어디에 둘지는 착수 시 정한다.
- **퀘스트 흐름 실행 방식도 미정이다.** 외부 그래프 플러그인을 새로 들이는 방식은 이미 있는 KataGraph·StateTree와 역할이 겹치므로
  우선순위를 낮게 본다.

## 남은 제한과 후속 작업

착수 시 plan에서 정할 질문:

1. 레코드 식별자: GUID, 행 ID, GameplayTag 중 무엇을 쓸지.
2. 배치: 새 위성 플러그인과 `KataFramework` 중 어디에 둘지.
3. 퀘스트 흐름 실행: KataGraph, StateTree, 단계 진행 규칙만 둔 전용 로직 중 무엇을 쓸지.
4. 세이브: 진행 상태·목표 카운트·월드 플래그를 저장할 계층을 이 작업에서 만들지, 별도 이슈로 먼저 만들지.
5. 분리: 범용 진행도 레코드 계층과 퀘스트 계층을 나눌지.
6. 알림 방식: 델리게이트와 메시지 라우터 중 무엇을 쓸지(라우터 보류 결정의 재검토 조건 확인).
7. 목표 감시자의 이벤트 소스: 사망, 아이템 획득, 상호작용(현재 없음).
8. 에디터 범위: 레코드 트리 편집, ID 선택기, PIE 중 상태 표시를 어디까지 제공할지.
