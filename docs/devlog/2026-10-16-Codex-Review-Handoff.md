# 커밋 직전 Codex 설명 검토 넘기기

작성: 2026-10-16  
갱신: 2026-10-16  
유형: 결정 기록  
대상: AGENTS.md "설명 변경의 공유 검토", [설명 변경 검토 사용법](../manual/Description-Review.md)  
기준: 커밋 `fc69b07`의 넘기기 규칙과 이후 작업 트리의 manual·지침 변경

## 배경과 결론

[처음 도입한 파이프라인](2026-10-12-Description-Review-Pipeline.md)은 AI 간 자동 실행을 두지 않고, 사용자가 Codex에서 ko-review의 `review` 스킬을 직접 실행했다. 사용자가 이 반복 작업을 없애고 싶다고 요청했다. 그래서 Claude가 커밋 직전에 `codex exec`로 해당 작업의 검토를 넘기도록 규칙을 바꿨다.

## 변경 내용

| 항목 | 이전 상태 | 반영 결과 |
|---|---|---|
| 검토 요청 | 사용자가 Codex에서 직접 실행 | 커밋 직전, `commit-doc-review`보다 먼저 Claude가 `codex exec`로 넘긴다 |
| 검토 범위 | Codex가 대기 항목을 고름 | 커밋할 작업의 목록 파일 하나만 지정하고, 설명 교정은 그 목록의 `taskPaths` 안으로 제한한다 |
| 호출 횟수 | 해당 없음 | 한 커밋에 한 번만 부른다. 검토 뒤에도 대기 항목이 남으면 사용자에게 보여 준다 |
| 스테이징 | 경로 단위 | 같은 파일에 다른 작업의 변경이 섞이면 이 작업의 변경 구간만 스테이징한다 |

## 주요 결정과 이유

넘기는 시점은 사용자가 요청할 때, 기록이 끝났을 때, 커밋할 때, 주기적으로 중에서 고르는 문제였다. 사용자가 커밋 직전을 택했다.

- 기록 직후에 넘기면 사용자 빌드 확인 뒤 설명이 다시 바뀌어 같은 항목을 두 번 검토할 수 있다. 빌드 확인과 문서 반영을 마친 뒤 커밋 직전에 넘겨 재검토가 생길 가능성을 줄인다.
- Codex가 설명을 고칠 수 있으므로 문서 반영 검토(`commit-doc-review`)는 Codex 뒤에 둔다. 그래야 Codex의 교정도 같은 커밋에 들어간다.
- 주기 실행은 대기 항목이 없어도 비용이 든다. 요청할 때만 넘기는 방식은 사용자가 지금 겪는 번거로움이 그대로 남는다.

여러 세션이 같은 작업 트리를 쓴다는 점도 따졌다. `review_queue.py`의 `begin`·`finish` 토큰과 스냅샷은 검토 기록만 지키고, Codex가 고친 파일 자체는 막지 않는다. 그래서 목록 하나만 넘기고, 수정 범위를 `taskPaths`로 제한하고, 커밋할 때 이 작업의 변경 구간만 고르게 했다.

호출을 한 번으로 묶은 이유는 항목끼리 서로를 근거로 삼는 경우 때문이다. Codex가 항목 B의 설명을 고치면, B를 근거로 둔 항목 A가 다시 대기로 돌아간다. 이때마다 다시 부르면 넘기기가 되풀이될 수 있다.

기존 절차에서는 사용자가 검토 요청을 전달했다. 이 변경은 플러그인 수정 없이 Kata의 AGENTS.md에 반영했으며, 프로젝트 지침이 플러그인 스킬보다 우선한다는 기존 원칙을 따른다.

## 첫 실행에서 드러난 문제

| 증상 | 원인 | 대응 |
|---|---|---|
| `The 'gpt-6.1-sol' model is not supported when using Codex with a ChatGPT account` | PATH의 npm 전역 CLI(0.125.0)가 Codex 앱 설정 모델보다 오래됐다 | 사용자 승인으로 CLI를 0.163.0으로 올렸다. manual 문제 해결 표에 적었다 |
| Codex가 두 문서를 교정했지만 `finish`를 남기지 않음 | 지시문의 "taskPaths 밖의 파일은 고치지 마"를 목록 파일 쓰기 금지로 해석했다. 목록 파일은 `taskPaths`에 없다 | 지시문에 "목록 파일에는 begin·finish로 기록"을 명시했다 |
| Codex가 스테이징 안내에 `git add -p`를 넣음 | 대화형으로 변경 구간을 고르는 안내였다 | 비대화형으로 구간을 고를 수 있도록, 기준 내용에 이 작업의 구간만 적용해 `git hash-object -w`·`git update-index --cacheinfo`로 올리는 방법으로 바꿨다 |

## 남은 제한과 후속 작업

- 고친 지시문으로 넘겼을 때 대기 항목이 `reviewed`로 기록되는지는 다음 커밋에서 확인한다.
- `git hash-object`로 구간만 스테이징하는 방법은 Git에만 쓸 수 있다. Diversion은 파일 단위로 커밋하므로, 다른 작업의 변경이 섞인 파일은 그 작업이 커밋할 때 함께 올린다.
